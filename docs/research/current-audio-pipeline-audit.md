# Current audio-only pipeline and timing seams

## Question and scope

This report answers [Audit the current audio-only pipeline and timing seams](https://github.com/200166shang/pyvideotrans/issues/4) from the source and tests at commit [`3eb3b2f`](https://github.com/200166shang/pyvideotrans/tree/3eb3b2f3ab11013632d5d35329620c861ce8df7c). It traces an English source programme through the existing CLI to translated speech, with special attention to the Alibaba-backed Qwen3 ASR, Alibaba/Qwen translation, and Qwen3 TTS implementations. No provider was called and no programme content or credentials were inspected.

## Answer in brief

The current CLI already accepts an audio file through the `vtv` path. It runs `prepare -> recogn -> diariz -> trans -> dubbing -> align -> recogn2pass -> assembling -> task_done` synchronously. An audio extension sets `is_audio_trans`, which skips video extraction and final video assembly, but it does **not** skip `align`: `align` is also the operation that joins per-subtitle TTS files into `target.wav`, and its no-rate path preserves source-subtitle gaps and pads to the source duration. The current audio result is therefore a WAV aligned to the source timeline, not a naturally paced MP3.

For the Alibaba path, the largest explicit serialization points are:

- Qwen3 ASR VAD-splits the input and sends every segment in a plain `for` loop, one request at a time.
- Translation batches lines but sends those batches one at a time; `trans_thread`/`aitrans_thread` are batch sizes, not worker counts.
- Qwen3 TTS inherits the generic per-line executor. The repository defaults are one TTS worker plus a one-second sleep after every generated line.

The smallest clean benchmark seam is the synchronous CLI orchestration function plus a new audio-only finalizer at the existing boundary immediately after `dubbing()`. At that point all expensive cloud stages have completed and `queue_tts` contains ordered segment filenames. A benchmark command can time each existing stage, concatenate those files in order with a declared natural-pause policy, encode MP3, and never call `align`, `recogn2pass`, or `assembling`. Reusing the current private no-rate aligner unchanged would retain source-timeline padding and would not meet the no-synchronization requirement.

## What actually runs for translated audio

## Sequential waits and concurrency limits

### Qwen3 ASR

Qwen3 ASR constructs its VAD-cut segment list before `_exec` ([`recognition/_qwen3asr.py`, lines 18-30](https://github.com/200166shang/pyvideotrans/blob/3eb3b2f3ab11013632d5d35329620c861ce8df7c/videotrans/recognition/_qwen3asr.py#L18-L30)). VAD defaults to speech chunks no longer than five seconds ([`_app_settings.py`, lines 158-168](https://github.com/200166shang/pyvideotrans/blob/3eb3b2f3ab11013632d5d35329620c861ce8df7c/videotrans/configure/_app_settings.py#L158-L168)); the base recognizer clamps this to at most 25 seconds ([`recognition/_base.py`, lines 150-170](https://github.com/200166shang/pyvideotrans/blob/3eb3b2f3ab11013632d5d35329620c861ce8df7c/videotrans/recognition/_base.py#L150-L170)).

Both Qwen3 request variants then iterate over segments sequentially. The SDK path makes one blocking request and optionally sleeps `asr_wait` before the next ([`recognition/_qwen3asr.py`, lines 31-79](https://github.com/200166shang/pyvideotrans/blob/3eb3b2f3ab11013632d5d35329620c861ce8df7c/videotrans/recognition/_qwen3asr.py#L31-L79)); the flash HTTP path does the same ([`recognition/_qwen3asr.py`, lines 98-159](https://github.com/200166shang/pyvideotrans/blob/3eb3b2f3ab11013632d5d35329620c861ce8df7c/videotrans/recognition/_qwen3asr.py#L98-L159)). There is no ASR worker pool or in-flight request window. `asr_wait` defaults to zero ([`_app_settings.py`, lines 170-175](https://github.com/200166shang/pyvideotrans/blob/3eb3b2f3ab11013632d5d35329620c861ce8df7c/videotrans/configure/_app_settings.py#L170-L175)), so the mandatory cost is serialized network/service latency rather than an intentional default sleep.

### Translation

The translator divides input into `trans_thread` or `aitrans_thread` sized chunks, but `_run_text` and `_run_srt` process those chunks in ordinary `for` loops and sleep after every request ([`translator/_base.py`, lines 46-71](https://github.com/200166shang/pyvideotrans/blob/3eb3b2f3ab11013632d5d35329620c861ce8df7c/videotrans/translator/_base.py#L46-L71), [`translator/_base.py`, lines 96-118](https://github.com/200166shang/pyvideotrans/blob/3eb3b2f3ab11013632d5d35329620c861ce8df7c/videotrans/translator/_base.py#L96-L118), [`translator/_base.py`, lines 142-160](https://github.com/200166shang/pyvideotrans/blob/3eb3b2f3ab11013632d5d35329620c861ce8df7c/videotrans/translator/_base.py#L142-L160)). The defaults are 10 lines for traditional translation, 50 SRT items for AI translation, and zero seconds between calls ([`_app_settings.py`, lines 170-174](https://github.com/200166shang/pyvideotrans/blob/3eb3b2f3ab11013632d5d35329620c861ce8df7c/videotrans/configure/_app_settings.py#L170-L174)).

Alibaba Machine Translation sends each traditional batch as one blocking `translate_with_options` call and retries only according to the global retry policy ([`translator/_ali.py`, lines 20-46](https://github.com/200166shang/pyvideotrans/blob/3eb3b2f3ab11013632d5d35329620c861ce8df7c/videotrans/translator/_ali.py#L20-L46)). Qwen MT likewise makes one blocking DashScope call per AI batch ([`translator/_qwenmt.py`, lines 32-73](https://github.com/200166shang/pyvideotrans/blob/3eb3b2f3ab11013632d5d35329620c861ce8df7c/videotrans/translator/_qwenmt.py#L32-L73)). Neither implementation adds concurrency.

### Qwen3 TTS

Qwen3 TTS does not override the generic `_exec`, so it uses `BaseTTS._local_mul_thread`. The base reads `dubbing_thread` and `dubbing_wait` from settings ([`tts/_base.py`, lines 40-46](https://github.com/200166shang/pyvideotrans/blob/3eb3b2f3ab11013632d5d35329620c861ce8df7c/videotrans/tts/_base.py#L40-L46)). At the repository defaults (`dubbing_thread=1`, `dubbing_wait=1`), it generates every subtitle line serially and sleeps one second after each line, including the last ([`tts/_base.py`, lines 143-165](https://github.com/200166shang/pyvideotrans/blob/3eb3b2f3ab11013632d5d35329620c861ce8df7c/videotrans/tts/_base.py#L143-L165), [`_app_settings.py`, lines 170-175](https://github.com/200166shang/pyvideotrans/blob/3eb3b2f3ab11013632d5d35329620c861ce8df7c/videotrans/configure/_app_settings.py#L170-L175)). If configured above one, it submits per-line work to a thread pool and waits for all futures; that branch does not apply `dubbing_wait` ([`tts/_base.py`, lines 167-195](https://github.com/200166shang/pyvideotrans/blob/3eb3b2f3ab11013632d5d35329620c861ce8df7c/videotrans/tts/_base.py#L167-L195)).

Each Qwen TTS line performs a blocking non-streaming DashScope call, then a blocking download, then conversion to WAV ([`tts/_qwentts.py`, lines 39-69](https://github.com/200166shang/pyvideotrans/blob/3eb3b2f3ab11013632d5d35329620c861ce8df7c/videotrans/tts/_qwentts.py#L39-L69)). Its retry decorator waits two seconds between retry attempts, but the repository default `retry_nums=1` permits only the initial attempt ([`tts/_qwentts.py`, lines 39-40](https://github.com/200166shang/pyvideotrans/blob/3eb3b2f3ab11013632d5d35329620c861ce8df7c/videotrans/tts/_qwentts.py#L39-L40), [`_app_settings.py`, lines 201-205](https://github.com/200166shang/pyvideotrans/blob/3eb3b2f3ab11013632d5d35329620c861ce8df7c/videotrans/configure/_app_settings.py#L201-L205)).

### Other concurrency that does not accelerate one CLI production run

The GUI queue system can create up to four workers per major stage for multiple production runs, with one second-pass recognizer ([`job.py`, lines 208-250](https://github.com/200166shang/pyvideotrans/blob/3eb3b2f3ab11013632d5d35329620c861ce8df7c/videotrans/task/job.py#L208-L250)). The CLI bypasses these queues and directly invokes the stage methods, so that worker count does not parallelize one CLI input. Audio speed adjustment can use up to 12 processes, but only when audio autorate creates speed-up work ([`_rate.py`, lines 466-483](https://github.com/200166shang/pyvideotrans/blob/3eb3b2f3ab11013632d5d35329620c861ce8df7c/videotrans/task/_rate.py#L466-L483)); it is not part of the recommended unsynchronized listening-edition path.

## Smallest clean seam for an audio-only CLI benchmark

Use the stage boundary immediately after `TransCreate.dubbing()` and before `TransCreate.align()`.

At that boundary:

1. `prepare`, `recogn`, optional `diariz`, `trans`, and `dubbing` remain the production implementations, so the benchmark measures the actual providers rather than a parallel harness.
2. `queue_tts` already contains the ordered translated text, voice choice, and generated segment filename for every accepted subtitle ([`_stage_dubbing.py`, lines 58-93](https://github.com/200166shang/pyvideotrans/blob/3eb3b2f3ab11013632d5d35329620c861ce8df7c/videotrans/task/_stage_dubbing.py#L58-L93)).
3. A small audio-only finalizer can concatenate existing segment files in queue order, apply one explicit natural-pause policy, and encode mono 64 kbps MP3. It does not need `novoice_mp4`, source timestamps, `SpeedRate`, second-pass ASR, subtitle embedding, or video assembly.
4. A sibling CLI orchestration function can wrap each stage with `time.perf_counter()`, record cache hits/retries and output duration, and write one structured production report. The existing `vtv_fun` is already the proven synchronous composition point; the new path only changes what happens after `dubbing()`.

Do **not** benchmark by chaining the existing `stt`, `sts`, and `tts` commands: that would benchmark three task wrappers and intermediate handoffs rather than the production composition. Do **not** reuse `SpeedRate._run_no_rate_change_mode` unchanged: it reads source timestamps, inserts their gaps, and pads to the original duration, exactly the coupling this benchmark must exclude.

For reproducibility, the command must explicitly distinguish cold and warm runs. `clear_cache` does not clear the global translation or dubbing caches, so merely passing the existing flag cannot guarantee a cold run. The production report should therefore include the audited commit, input content hash and duration, provider/model identifiers, non-secret settings, cache policy and hit counts, per-stage and total monotonic durations, retry counts, output duration, and measured/estimated cloud cost. The fixed benchmark sample itself should remain outside the repository if it is not public.

## Decision supported by this audit

Create an audio-only CLI benchmark as a thin sibling of `vtv_fun`, not as a rewrite of the task model. Reuse the pipeline through `dubbing()`, add a dedicated natural-pacing MP3 finalizer, and instrument the orchestration boundary. Before claiming provider performance gains, fix or explicitly control the current serial Qwen3 ASR loop, translation batch semantics, one-worker/one-second TTS default, and hidden global cache state.
